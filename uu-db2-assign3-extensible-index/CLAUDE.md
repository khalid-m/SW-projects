# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a university assignment (Uppsala University, Database Technology 2, Assignment 3) built on **AMOS2**, an extensible object-relational DBMS with its own query language (AmosQL/OSQL) and a Lisp-based extension mechanism. The goal is to implement a custom **KD-tree index type** so that Euclidean-distance proximity queries over wine-sample feature vectors are rewritten transparently by the AMOS query optimizer to use the KD-tree instead of a full scan.

The assignment requires AMOS2 itself (`amos2.zip`, containing `amos2/bin/javaamos.jar` etc.) to be present as a sibling directory (`../amos2`) — it is not part of this repo and must be downloaded/unzipped separately per `readme.txt`.

## Key files

- `KDTreeIndex_Stub.java` — Java foreign-function implementation backing the KD-tree index (uses Simon Levy's `edu.wlu.cs.levy.CG.KDTree` from `kd.jar`, plus AMOS2's `callin`/`callout` Java-callout API). Implements `kdtree_make`, `kdtree_put`, `kdtree_get`, `kdtree_delete`, `kdtree_clear`, and `kdtreeProximitySearch`. Multiple KD-trees are kept in a static `Hashtable<Integer, KDTree<Oid>>` keyed by an integer id generated by `kdtree_make`.
- `lab3_stub_sol-notJavaFile.java` — despite the `.java` extension/filename, this is actually the **AmosQL solution script** (same content shape as `lab3_stub-empty.osql`, but with exercises worked out and execution-plan output pasted in as comments). Treat it as OSQL, not Java.
- `lab3_stub-empty.osql` — the blank/starting AmosQL script with `TODO` markers for each exercise; this is the file a student fills in.
- `kdtree.lsp` — Lisp snippet loaded via `load_lisp('kdtree.lsp')` from OSQL. Registers the optimizer rewrite rule that maps calls to `euclid(Vector, Vector)->Number` onto `kdtreeProximitySearch`, so declaring a KDTREE index on a column makes the optimizer substitute the index automatically. Must be left intact (per `readme.txt`).
- `winequalitysample.csv` — the dataset (2939 wine samples); must not be modified, or the validation script may fail.
- `kd.jar` — third-party KD-tree implementation (compiled classes only, no source in repo).
- `setup.cmd` / `assignment3.cmd` — Windows batch scripts that set `JAVA_HOME`/`PATH`/`CLASSPATH` (pointing at `../amos2/bin`, `kd.jar`, and `javaamos.jar`) and launch the environment.

## Architecture: how the pieces connect

1. **OSQL type/schema layer**: `create type WineSample`, plus stored functions `wsId` and `features` define the schema; wine rows are loaded from the CSV via `read_ntuples` + `addwinesample`.
2. **Foreign functions**: OSQL `create function ... as foreign 'JAVA:KDTreeIndex_Stub/<method>'` declarations bind AmosQL function names directly to methods in `KDTreeIndex_Stub.java`. Each Java method receives `(CallContext cxt, Tuple tpl)`, reads its arguments positionally out of `tpl` via typed getters (`getIntElem`, `getDoubleElem`, `getSeqElem`, `getOidElem`), and returns results by mutating `tpl` and calling `cxt.emit(tpl)` (possibly multiple times, e.g. for the proximity search's result bag).
3. **Manual index usage** (`kdtree_make`/`kdtree_put`/`kdtreeProximitySearch` called directly from OSQL) demonstrates a KD-tree used as an ordinary auxiliary structure, distinct from the query optimizer.
4. **Transparent extensible indexing** (the assignment's real point): `register_exindextype('KDTREE', FALSE)` registers a new index type backed by the same foreign functions (`kdtree_make/put/get/delete/clear`), then `load_lisp('kdtree.lsp')` installs an *index rewrite rule* mapping the built-in `euclid` distance function to `kdtreeProximitySearch`. After `create_index("features", "f", "KDTREE", "multiple")` and `reoptimize(...)`, queries written against `euclid(...)` (e.g. `closeWineSamples`) get their execution plan automatically rewritten by AMOS to use the KD-tree index — no application code change needed. The script also compares this against a built-in `XTREE` index type for the same column to contrast execution plans/performance.
5. Progress is checked at each stage using `pc("<functionName>")` (print execution plan) and repeated invocations to compare timings before/after indexing.

## Build & run

Requires AMOS2 (`amos2.zip`) unzipped as a sibling directory to this repo (i.e. `../amos2`), and a JDK compatible with `kd.jar`/AMOS2's javaamos (scripts reference JDK 1.7, but any JDK producing compatible class files works).

```
# One-time: set env (Windows/cmd) — sets JAVA_HOME, PATH, CLASSPATH (../amos2/bin, kd.jar, javaamos.jar)
setup.cmd

# Compile the Java foreign functions
javac KDTreeIndex_Stub.java

# Launch the AMOS2 Java interpreter (JavaAmos)
javaamos
```

At the `Javaamos N>` prompt, paste/execute statements from the OSQL script (`lab3_stub-empty.osql` while working the assignment, or `lab3_stub_sol-notJavaFile.java` as the reference solution) one at a time — the script is meant to be run interactively so execution plans (`pc(...)`) and timings can be inspected between steps, not executed as a single batch file.

There is no automated test suite; correctness is verified interactively by comparing `pc(...)` execution plans and query timings before/after each indexing exercise against the expected output already recorded as comments in `lab3_stub_sol-notJavaFile.java`.
